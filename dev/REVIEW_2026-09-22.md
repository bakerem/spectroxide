## 2. Physics

### P-1 (high priority): the BR Gaunt factor uses x = hν/kT_z where it needs x_e = x/ρ_e (verified)

- **Where:**
  - `src/solver.rs:572-581` builds `expc_grid` from `grid.x`.
  - `src/bremsstrahlung.rs:265` and `:337-338` evaluate the fit on that x.
  - The derivative at `:396-399` has the same error.
  - `br_emission_coefficient` (`:153`), `br_rhs` (`:473`), and `src/greens.rs:431` also pass grid x.
- **References:** the physical Gaunt factor depends on hν/kT_e and T_e, never on T_z.
  - **Chluba, Ravenni & Bolliet (2020), MNRAS 492, 177 (arXiv:1911.08861), Sect. 4:** the paper this code already cites for its Gaunt treatment. It defines the thermally averaged Gaunt factor as ḡ(ω, θ_e), with ω = hν/m_ec² (equation `gaunt_def_usual`, about Eq. 23; I counted the equation number by hand, so it may be off). Its discussion of that equation uses x = ω/θ_e, which is hν/kT_e.
  - **Chluba & Sunyaev (2012), MNRAS 419, 1294, Eq. `K_BR`:** writes K_BR ∝ θ_e^{−7/2} e^{−xφ}/φ³ Σ Z²N g_ff(Z, x, θ_e). The Boltzmann factor there is e^{−x_e}, but the Gaunt argument is written as x. The notation is ambiguous. The paper points to Itoh et al. (2000) for g_ff, and those fits take hν/kT_e.
  - **Textbooks:** Draine (2011), *Physics of the Interstellar and Intergalactic Medium*, Eq. 10.9 (not checked against the page); Rybicki & Lightman (1979), Sect. 5.3, thermal Gaunt factor as a function of u = hν/kT (I am confident of the section, not of an equation number).
- **Evidence:** the fit's constant 1.425 equals (√3/π) ln(C/2.25) − 1 = 1.42537, where C = 2^{5/2} e^{−5γ_E/2}/α = 183.107. So the fit's low-frequency limit is the classical Gaunt factor (Draine 2011, Eq. 10.9), which depends on ν/T_e. Its ½ ln θ_e term matches only if the variable is x_e. Two agents derived this independently and found it with mpmath.
- **Impact:** g is overestimated by (√3/π) ln(1/ρ_e).
  - Before recombination, |ρ_e − 1| is about 1e-5, so the effect is negligible.
  - At z = 100 (ρ_e ≈ 0.62, estimated, not taken from the solver), BR is too large by 7–9% for x from 1e-4 to 1e-2.
  - At z = 200 the error is about 2–3%.
  - This matters for absorption of low-x photon injection after recombination: the dark-photon and axion limits, and `photon_injection_validation`.
- **Fix:**
  1. Multiply `ea_Z` by ρ_e^{√3/π}, since exp(−S3 ln x_e) = x^{−S3} ρ_e^{S3}.
  2. In the ρ_e derivative, change the ½ in `d_species` to 3/2.
  3. Apply the same change to the other call sites listed above.
  4. Rewrite the docstring: the ½ ln θ_e term is the classical θ_e^{1/2} dependence, not an empirical interpolation. This also answers the old warning F4, which called 1.425 "unverifiable".
- **Tests:**
  - At fixed ν and T_e, vary θ_z. The quantity K_BR φ³ e^{x_e} θ_e^{7/2}/Σ must stay the same.
  - At low x_e, compare g with the Draine expression, typing C = 183.107 into the test as a literal.
  - Replace `tests/greens_function_checks.rs:326-336` (see P-6).
- **Verify after the fix:** rerun the post-recombination photon-injection notebooks and the dark-photon limits, then state the shift in the FIRAS limit. Run the physics-inquisitor agent on the diff.

### P-2 (medium, documentation): the `f_inj` recipe has a spurious factor of 2 (verified)

- **Where:** `src/energy_injection.rs:128-130` gives f_inj ≈ 2(Ω_cdm/Ω_γ) f_dm G₃/(G₂ x_inj,0).
- **Evidence:** Bolliet & Chluba 2021 (arXiv:2012.07292), `eq:f_inj`, has no factor of 2, because the two photons per decay cancel against m_X = 2E_inj. The verifier also took the moments of the code's own source term and got f_inj = (G₃/G₂) f_dm Ω_c/(Ω_γ x_inj,0). It reproduced the paper's coefficient 1.31×10⁴.
- **Impact:** a user who follows the doc injects twice the energy. No code path converts f_dm to f_inj; `cli.rs:1156` and `solver.py:237` pass the value through unchanged.
- **The paper is correct; only our doc comment is wrong.** The paper's equation is f_inj = f_γ N_X,0/N_γ,0 = (G₃/G₂)(ε/x_inj,0)(ρ_X,0/ρ_γ,0) ≈ 1.31×10⁴ ε f_dm/x_inj,0 × (Ω_cdm h²/0.12). Our comment also drops the paper's ε, the fraction of the rest mass that goes into photons.
- **Fix:** replace the comment with the paper's equation, including ε. Add a test that sets f_inj from the paper's equation and asserts the PDE injects Δρ/ρ = f_dm(Ω_c/Ω_γ)∫Γe^{−Γt} dt/(1+z) to 1%.

### P-3 (medium, documentation and warning text): wrong stimulated-decay factor and "lower bound" claim (verified)

- **Where:** `src/energy_injection.rs:106-115`, `:925-943`, and `:1355-1372` (the `warn_stimulated_emission` text).
- **What is wrong:**
  - **Factor:** the code states (1+n)², which is the forward rate only. The net rate for a boson X → γγ is 1+2n, because inverse decay cancels the n² term (Bolliet & Chluba 2021, `eq:stim-boltz_simp`). At x = 0.05 the correct factor is 40, not 420 or the comment's "≈ 440".
  - **Explanation:** "both photons in the same mode" is wrong, because the photons travel back to back.
  - **"Lower bound":** this is false. Stimulated decay moves injection earlier, where it thermalizes, and the same paper reports weaker constraints. When Γt₀ ≪ 1 the sign flips, so the vacuum result is neither an upper nor a lower bound.
  - **Suggested fix in the comment:** it says to multiply the rate but keep S = exp(−Γt). That breaks particle-number bookkeeping. The paper replaces t with t_stim.
- **Decision (2026-09-22):** no change.

### P-8 (question, needs a run): DC and BR relax toward T_e with the injection part removed

**What the code does.** Heat injection at rate q raises the electron temperature above the Compton equilibrium ρ_eq of the current photon field:

- `solver.rs:937` sets δρ_inj = q t_C/(4θ_z).
- The backward-Euler T_e step (`solver.rs:1009-1040`) solves dρ_e/dτ = R[(ρ_eq + δρ_inj − H_dcbr) − ρ_e] − H t_C ρ_e.
- DC and BR emission then relax the photon spectrum toward n_pl(x/ρ_dcbr), not n_pl(x/ρ_e) (`solver.rs:1176-1198`). The target is ρ_dcbr = ρ_e − R δρ_inj Δτ/[1 + Δτ(R(1+H′) + H t_C)], clamped to [0.5, 2].
- In words: DC and BR see a T_e with the heating-driven excess removed.

**Why the justification is wrong (verified).** The comment says that using the full ρ_e would count the injected energy twice. It does not:

1. The photon rows gain energy from DC and BR through Δτ·em·(neq − Δn) (`kompaneets.rs:901-919`).
2. The electron row loses H_dcbr, built from the same `em` and `neq` arrays (`kompaneets.rs:978-991`).
3. So whatever target is used, the energy DC and BR give the photons is exactly the energy the electrons lose. With the full ρ_e, the extra low-x emission is paid out of δρ_inj. It is not added on top.

Physically, DC and BR drive n toward a Planck spectrum at the actual T_e. That is the form in Chluba & Sunyaev (2012), Eq. 8, which the code comment itself cites.

**What using the actual T_e would change.** While heat goes in, the electrons are hotter than Compton equilibrium by δρ_inj. At x ≲ x_c, DC and BR would then emit slightly more soft photons. More photons means a slightly smaller μ, with the same total energy.

**Which runs are affected:**

- **Affected:** heat-injection scenarios only: single burst, decaying particle, s- and p-wave annihilation, tabulated heating, and custom heating. Continuous scenarios keep δρ_inj nonzero during the whole solve; a burst has it only during the burst.
- **Unaffected:** photon injection, dark photon, and axion. Their `heating_rate` is zero, so δρ_inj = 0 and the subtraction does nothing.

**Size (disputed, no run yet):**

- **First reviewer:** about 0.8% in μ at z = 2e6. This looks like the ratio δρ_inj/Δρ_eq ≈ 6e-3, without the extra 1/x weighting of the μ distortion near x_c.
- **Verifier:** δμ/μ ≈ δρ_inj x_c/μ ≈ 4e-5 to 1.4e-4 at z = 2e6, and a few e-6 at 2e5. This is an order-of-magnitude estimate with the logarithm cut at x_c.
- **Visibility:** if the verifier is right, the effect is far below the 2–5% agreement with the Green's function and CosmoTherm, and invisible in every figure. If the first reviewer is right, it is visible in deep-μ comparisons.

**A second issue in the same code (my reading, not verified).** The subtraction removes R δρ_inj Δτ/denom, which is the injection added in the current step only. In the tightly coupled regime (R Δτ ≫ 1, before recombination) that equals the whole excess δρ_inj/(1 + H′). When R Δτ ≲ 1 (after recombination), it removes only this step's increment, while heat from earlier steps stays in ρ_e. So the treatment differs by regime and depends on step size in between. If the subtraction stays, this dependence on Δτ is a candidate contributor to the first-order-in-Δτ energy residual (`dev/audit/energy_conservation_audit.md:136-143`).

**Also:** the clamp to [0.5, 2] can hide a bad ρ_e without warning. ρ_e ≈ 0.6 at z = 100, which is close to the lower limit.

**Measured (2026-09-22).** The A/B run settles the size dispute. Δμ/μ is −5.6e-5 at z_h = 2e6, −1.9e-5 at 5e5, and −2.0e-5 at 2e5. For a decaying particle it is −2.9e-5. Energy closure changes by at most 3e-7. The shift is the same at Δτ_max = 10, 3, and 1, so the regime-dependent subtraction is not a measurable part of the energy residual. The clamp never engaged: ρ_e stayed in [0.988, 1.000013] down to z = 500. The first reviewer's 0.8% is wrong. The verifier's estimate holds at 2e6 and is 5 times too low at 2e5. Decision: ADR 2 (switch to the actual T_e), accepted 2026-09-22.

**What I don't know:** which target CosmoTherm uses. If it uses the actual T_e and the verifier's estimate is right, the difference is still invisible in the CosmoTherm comparison.

## 3. Robustness

### R-1 (high): small grids return wrong answers with exit status 0 (reproduced)

- **Where:** `src/grid.rs:105` accepts `n_points >= 10`. No check after the solve compares the energy in the spectrum with the energy injected.
- **Single burst** (`solve single-burst --z-h 2e5 --delta-rho 1e-5 --z-end 1e5`):
  - `--n-points 100`: Δρ/ρ = −1.5e-2 and μ = −6e-3, exit 0.
  - `--n-points 50`: panics at `solver.rs:893`.
  - `--n-points 200`: correct.
- **Constant tabulated heating** (the correct value is 2.9e-4):
  - 300 points: +83%.
  - 1000 points: +3%.
  - Python passes `n_points` through unchanged.
- **Fix:**
  1. Raise the floor, or warn below the tested range (about 500).
  2. After the run, compare `drho` with the known injected Δρ/ρ (burst, tabulated ∫dq/dz). Above 5% disagreement, warn; the stricter alternative is an error.
  3. Add a test at the smallest accepted grid.

### R-2 (medium): invalid tolerances pass validation (reproduced)

- **Photon-source step cap:** a value of 0, a negative value, or NaN for `dtau_max_photon_source` switches the cap off silently (`solver.rs:815`). One photon run went from 19,027 steps to 4,135. `--nc-z-min -1` is also accepted.
- **Fix:** in `SolverConfig::validate`, require these to be finite and greater than 0.
- **`z_end = 0`:** runs 5,000,000 steps down to z = 4e-323, then advises "increase dtau_max" (`solver.rs:86`). Require `z_end > 0`.

### R-3 (medium): parameters are accepted and ignored (reproduced)

- **Ignored `--delta-rho`:** every scenario except `single-burst` ignores `--delta-rho` (`cli.rs:341`, `:1102-1170`), yet it still triggers the "strong distortion" warning. Python always appends it, and `solve(dq_dz=..., delta_rho=...)` ignores it.
- **Ignored `--dn-planck` and `--threads`:** `--dn-planck` is in the shared `SOLVER_KEYS` list (`cli.rs:302`) but only `solve` reads it; the sweeps ignore it. `--threads` has no effect in `solve`.
- **Parser:** duplicate flags use the last value, stray positional words are dropped, and `--n-points 0` means "use the default" (`cli.rs:636`, `:1284`).
- **Fix:** give each subcommand its own list of allowed flags, and reject duplicates and positional arguments.

### R-4 (medium): Python runs a stale binary without warning (inferred; happened before per `dm_comparison_residual.md:255`)

- **Where:** `solver.py:325-329` builds the binary only if it does not exist.
- **Hash check:** `get_physics_hash` reports the stale binary's own hash, so the table hash check also passes.
- **Fix:** if any `src/**/*.rs` file or `Cargo.toml` is newer than the binary, warn or rebuild.

### R-5 (medium): progress messages go into `warnings` (reproduced)

- **Where:** `solver.rs:1608` pushes "Progress: …" into `diag.warnings`, and `solver.py:398` re-raises each entry as `RuntimeWarning`.
- **Effect:** under `-W error`, a valid run fails.
- **Fix:** send progress to stderr only.

### R-6 (medium): the Python wrapper fails on Windows (inferred)

- **Binary name:** `solver.py:324` looks for a binary without `.exe`, so it never finds it and rebuilds on every call.
- **Working directory:** the `cargo run` fallback has no `cwd=` (`solver.py:353`).
- **Fix:** add the `.exe` suffix when `os.name == "nt"`, and pass `cwd`.

### R-7 (low)

- **Keyword check after the solve:** `solve()` checks for unknown keywords after it runs the solve (`solver.py:1645`). A typo wastes the whole run; see A-1.
- **Broad `except` in table loaders:** `load_or_build_*_table` (`greens_table.py:1139`, `:1186`) catches every `Exception`. A missing binary, or a hash mismatch under `-W error`, therefore starts a rebuild that takes hours, instead of reporting the cause. Catch `(OSError, KeyError, ValueError)` only, and log the reason.
- **Unchecked `greens` input:** `greens --z-h -5` exits 0 with `"gf_mu": null`, and an empty `--z-injections` exits 0 with no results.
- **Silent fallbacks in Python:**
  - `_run_tabulated_photon` caps `n_z` at 500 without saying so.
  - `r.get("pde_mu", r.get("gf_mu", 0.0))` returns 0.0 if the schema drifts.
  - A NaN μ becomes `None`.
  - `validate_cosmology` skips any mapping that is not a `dict`.

### Checked and found clean

- **Unsafe code:** every `get_unchecked` in `kompaneets.rs` is covered by an entry `assert!`.
- **Table loaders:** they reject NaN, duplicate, unsorted, and ragged input.
- **Recombination:** it uses no global cache, so it has no thread-safety issue.
- **JSON output:** the float and string escaping are correct.
- **Defaults:** the Rust and Python defaults for `z_end`, `dtau_max`, `nc_z_min`, and `dtau_max_photon_source` agree.
